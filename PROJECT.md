# Quriliş Go — память проекта (для разработчиков и AI-ассистентов)

Один файл о том, как устроен проект, где что лежит и какие решения уже приняты. Обновляйте при крупных изменениях.

## Что это
Маркетплейс строительных магазинов Ташкента: каталог с ценами и остатками магазинов, доставка Яндекс, Usta AI
(подбор материалов), 3D-дизайнер комнат, мастера.
**Telegram убран из интерфейса (02.11.2026, решение владельца):** на сайте и в приложении нет входа через Telegram,
привязки уведомлений, ссылок на бота и канал, панели автопостов. Вход — по номеру телефона (SMS), уведомления — push и SMS.
Серверный модуль бота (`bot.js`, `telegram.js`, `channel.js`) пока остаётся в коде, но без `TELEGRAM_BOT_TOKEN` не запускается;
`SMS_MODE=telegram` на боевом сервере больше не годится — сайт не показывает вход через бота, нужен договор SMS (Eskiz).
Поле «Telegram магазина» в контактах магазина оставлено: это контакт самого магазина, не бот.
Языки: русский, узбекский (новая латиница ö ğ ş ç), английский. Бренд: в тексте **Quriliş Go**, в логотипе **qurilish go**.
Цвета: teal `#0B6E69`, orange `#D9530A`, ink `#131B1A`, paper `#F3F5F2`.

## Как устроен клиент (`src/page.html`)
- Тексты: `L(ru, uz, en)`. Узбекский в исходнике может быть в старой орфографии — `uzNew()` переводит на выходе.
  Английский берётся из словаря `EN[ru]` (ключ — точный русский текст); шаблонные строки передают английский третьим аргументом.
  Новый текст: добавьте пару `L("…", "…")` **и** ключ в `EN` (иначе в EN покажется русский). Словарь собирается
  скриптами из `scratchpad/agents/en` (extract.py / merge.py) — при отсутствии просто добавьте ключ в объект `EN` вручную.
- Числа: `fmt`/`fmtN` (разряды по языку), десятичный разделитель `DEC`, локаль дат `LOCALE` — меняются в `syncLangFormats()`.
- Режимы: `API` пуст → демо (localStorage); `API` задан → `apiBoot()` → `/api/config` → `syncCatalog()`.
  `preLaunch()` (сервер подключён, товаров < 12) → главная «Скоро открытие» (`renderHomeLaunch`).
- Поиск: `smartSearch()` — транслит, стемминг, синонимы `SK_SYN`, опечатки (Дамерау-Левенштейн); индекс включает ru/uz/en.
- Дизайнер: `DS` состояние, `dsEstimate()` смета, фото-режим — WebGL2 SDF-шейдер `DS_PHOTO_FS` (`dsPhoto*`).
- Эффекты (`html.fx`, только компьютер с мышью или «Эффекты: вкл»): всё, что движется каждый кадр, двигается через `transform`/`opacity`
  на отдельном элементе — свечение героя `.hero-glow`, подсветка карточки `.glow` (создаётся при наведении), бегущая рамка `.askbar::before`,
  курьер на карте `.truckel` (`offset-path`, пауза вне экрана через IntersectionObserver). Движения мыши сводятся к одному обновлению на кадр
  (`pointerFrame`). Не возвращайте SMIL `animateMotion`, `filter: blur` в анимациях и `will-change` на всех карточках: это и было причиной
  рывков в Safari. Мерить: `scratchpad/perf/measure2.js`, `trace2.js`, `idle.js` (Chromium, троттлинг CPU 4×).
- Роутер: `route = { view, cat, … }`, хэш `#catalog`, `#cat-<id>`, `#p-<id>`, `#design`, `#masters`, `#seller`, `#store-<id>`, `?lang=en`, `?q=`.
- Главная из виджетов: каждый блок `renderHome` помечен `data-w="<id>"` из реестра `HOME_W`; `applyHome()` расставляет блоки в сохранённом
  порядке и прячет выключенные. Настройка — «Настроить главную» (`dHomeSetup`, ключ `imorat.home` на компьютере и `imorat.home.m` на телефоне).
  На телефоне по умолчанию выключены `PHONE_OFF` (преимущества, бегущая строка, доставка, новинки, зима), калькуляторы показаны чипами,
  категории — сеткой 4×2, комплекты и мастера листаются горизонтально, магазины — первые пять и «Все магазины».
- Вход: только номер телефона (SMS) и Telegram. «Войти через Telegram» — `POST /api/auth/tg/start` (билет) → бот `t.me/<bot>?start=login_<ticket>`
  (новому чату бот предлагает поделиться номером) → бот показывает «🔐 Вход на сайт… Это вы?» с кнопками «✅ Да, это я» / «❌ Нет»
  (с IP запроса) и привязывает билет только после «Да» — ссылку `login_<ticket>` можно подсунуть кому угодно, и без подтверждения
  её открытие логинило бы отправителя под аккаунтом жертвы → страница опрашивает `GET /api/auth/tg/poll?ticket=` раз в 2 с (`tgLoginStart`).
  Google/Apple на сервере остались (`/api/auth/google|apple`), но на сайте не показываются. После регистрации спрашиваем только имя и
  «Кто вы?» (покупатель / мастер −3% / магазин); район — при оформлении. Роль меняется в профиле (`#roleBox` → `PATCH /api/me {role}`).
- Карта адреса (`initPickMap`): настоящая улица-дом карта с меткой в центре — двигаете карту, адрес под меткой подставляется в поле
  (`geoReverse`), а ввод адреса даёт подсказки (`bindAddrSuggest` → `geoSuggest`), выбор подсказки переносит карту. Источник: Яндекс Карты
  (ключ `IMORAT_YMAPS_KEY` в config.js / `YANDEX_MAPS_KEY` на сервере → JS API 2.1 + SuggestView + геокодер), иначе тайлы OpenStreetMap
  и геокодинг через `/api/geo/suggest|reverse` (`server/src/geo.js`: Яндекс-геокодер с ключом, иначе Nominatim с кэшем и 1 запросом/с);
  в демо без сервера — Nominatim прямо из браузера.
- Инструменты: нижняя вкладка «Инструменты» на телефоне и ряд `tools` под героем (калькуляторы, Usta AI, 3D-дизайнер, мастера,
  список по фото, доставка) открывают панель виджетов (`openWidgets`).
- Тема: `themePref` auto/light/dark (`imorat.theme`), кнопка солнце/луна в шапке (`theme-toggle`) и переключатель в профиле; тёмные
  цвета — `:root[data-theme="dark"]` и `prefers-color-scheme`. `applyLook()` держит `<meta name="theme-color">` в цвете шапки.

## Как устроен сервер
- `.env` — см. `server/.env.example`. В проде сервер не стартует с SMS в dev-режиме (`ALLOW_DEV_SMS=1` только на тесте).
- `DEMO_STORES=0` — без 9 демо-магазинов (реальный запуск); `dropDemoStores()` удаляет их из существующей базы.
- Роли: покупатель / `pro` / продавец (`store_id`) / админ (`ADMIN_PHONES` + TOTP). `needSeller` блокирует магазины `blocked/rejected`;
  `pending` может готовить товары — они скрыты до одобрения (каталог берёт офферы только магазинов `active`).
- Бонусы: кешбэк 1 % (2 % pro; все ставки только в `.env` сервера, клиент хранит одну копию для демо), потолок `BONUS_MAX_CASHBACK` за отправление, не начисляется владельцу на свой магазин;
  приветственный и реферальный бонусы — после **первой доставки** друга; лимит приглашений `BONUS_MAX_INVITES`/мес.
- Лимиты: OTP по IP щедро (CGNAT), строго по номеру; импорт прайса 20/сутки, новых товаров 500/сутки, фото 100/сутки на магазин.
- Комиссия: `COMMISSION=*:1` (наша, по категориям) + `ACQUIRING_PERCENT=2` (эквайринг Payme/Click по тарифу договора, можно `payme:2,click:1.8`; отдельная строка `acquiring`
  в `shipments`/финансах); обе только с картовых заказов, фиксируются при создании заказа. `PROMO_MONTHS=3`: `stores.free_until`
  ставится при одобрении (для уже активных — от `created_at`), в этот период наша комиссия 0, эквайринг остаётся;
  админ меняет `free_until` через `PATCH /api/admin/stores/:id` (`""` — закончить сейчас). Ставки: `/api/config.{commission,acquiring,promo_months}`,
  `/api/seller/summary.rates = {platform, acquiring, promo_months, free_until, promo}`.
- Оплата картой (`payments.js`): Payme Merchant API (JSON-RPC `/api/pay/payme`) и Click SHOP API (`/api/pay/click`). Онлайн-заказ создаётся
  с отправлениями `unpaid` (магазин их не видит), после callback «оплачено» → `new` + уведомления; не оплаченные за `PAY_TIMEOUT_MIN`
  отменяются в `sweep`. Отмена оплаченного отправления → `pay_status=refund_due` и сообщение админам (возврат пока вручную в кабинете провайдера).
  Финансы магазина: `balance = вся комиссия + доставка, полученная магазином с покупателей (store/cash) − деньги за товар по картовым заказам,
  которые держит Quriliş Go (`online_held`) − расчёты`; `payout_due` = доля магазина (товар − комиссия − эквайринг) по картовым заказам, включая заказы
  со статусом `refund_due` (другой магазин отменил свою часть). Админ может пометить заказ «оплачен» вручную — это запускает `orderPaid()`.

### Достоверность данных в рабочем режиме (ноябрь 2026)
- **Контракт API**: `API_CONTRACT` в `index.html` ↔ `server/src/app.js` (`/api/health` отдаёт `contract`, `min_client`). Клиент при
  старте делает `apiProbe()`: нет ответа → `apiState = "offline"` (плашка `#apiBar`, последний настоящий каталог из
  `localStorage imorat.apiCat` с датой, оформление заблокировано); несовпадение → `"incompatible"` («Обновите приложение»).
  Встроенный демо-каталог в рабочем режиме не показывается никогда. Магазинная сборка (`app/scripts/prepare-www.mjs --release`)
  опрашивает `/api/health` и `/api/config` и отказывается собираться при недоступном/чужом сервере, расхождении контракта,
  `SMS_MODE=dev` или демо-магазинах. `IMORAT_SITE_URL` — только явная настройка (config.js / переменная / `SITE_URL` сервера).
- **Цены**: у каждого оффера `upd` (последняя правка или подтверждение `stores.prices_confirmed_at`); `freshness()` на клиенте,
  старше 7 дней — предупреждение; `/api/seller/offers/confirm`; напоминание продавцу в Telegram раз в неделю (`priceReminders`).
- **Стоимость**: чекаут запрашивает `/api/quote` (`requestServerQuote`, дебаунс 350 мс), кнопка оплаты заблокирована до ответа;
  `expectTotal` = сумма сервера → `POST /api/orders` с `expected_total` → `409 total_changed` при изменении. Яндекс без цены →
  `quote.unknown`, `del/total = null`, «—», заказ `503 delivery_price_unavailable`.
- **Габариты**: `products.dims` ([д, ш, в] м; продавец задаёт в см) или типовые по подкатегории (`catalog.json.bulky`);
  `pickTariff(kg, len)` на обеих сторонах (`LONG_S` 1,8 м → малый фургон, `LONG_L` 4,5 м → большой); размеры уходят в заявку
  Яндекса; поля `access` (подъезд машины) и `elevator` → комментарий водителю и карточка заказа у продавца; отказ Яндекса в
  грузчике → повтор заявки без него, `shipments.loaders_failed`, уведомления покупателю и админам.
- **Курьер**: `/api/orders/:num/courier` → координаты Яндекса или `{ pos: null, unavailable: true }`; симуляция только при
  `COURIER_SIMULATION=1` (в production запуск запрещён).
- **Повтор заказа**: `repeatOrder()` → `/api/quote` → экран сравнения (цена/остаток/нет в продаже), замены магазина и изменённые
  строки только с подтверждением. **Список/фото**: строки без нужного остатка помечаются и в корзину не идут.
- **Отчёт продавца**: `/api/seller/statement?month=` (продажи, возвраты, комиссия, эквайринг, другие записи, к выплате,
  дата окончания бесплатного периода) + CSV на клиенте; слово «прибыль» не используется.

### Этап 0 — запуск без договоров (ноябрь 2026)
- `cfg.payOnReceipt` = `ALLOW_PAY_AT_STORE=1` и ни одного платёжного провайдера; `cfg.deliveryBy` = `yandex` (есть токен) /
  `store` (этап 0: магазин возит сам) / `platform` (карты есть, Яндекса нет — тариф формулы, курьера вызывает платформа вручную).
  `/api/config` отдаёт `pay_on_receipt`, `delivery_by`; клиент — `stage0()`, `storeDelivers()`.
- При `deliveryBy = store`: в `quote` у отправлений `price: null, source: "store"`, `del: null`, `total` = товары,
  `delivery_by: "store"`; заказ хранит `form.delivery_by`, `shipments.price = 0`. Поток статусов `STEPS.store`
  (new → assembling → on_way → delivered), кнопки продавца и бота «Курьер выехал» / «Доставлен», тексты покупателю про курьера
  магазина. Клиент: «Доставка магазином», «доставку уточнит магазин», «Итого за товары», оплата «При получении».
- `storeFinance.delivery_due` считается только по отправлениям с настоящей заявкой Яндекса (`claim_id` не `sim-`) — магазин
  ничего не должен за доставку, которую платформа не заказывала. Установщик требует токен бота и ставит `ALLOW_PAY_AT_STORE=1`.

### Роли: владелец и помощники (ноябрь 2026)
- `roleOf(u)` в `app.js`: телефон из `ADMIN_PHONES` → `owner`; строка в `staff` (не отключённая) → её роль (`owner` для строки из
  `.env`, `admin` для помощников). `needAdmin` — модерация/заказы/жалобы; `needOwner` — финансы, выплаты, settlements, пометка
  оплаты, дашборд, аудит, канал, управление сотрудниками.
- Владелец по паролю: `OWNER_LOGIN` + `OWNER_PASSWORD_HASH` (scrypt, `tools/owner.mjs`, команда `imorat owner`; в `.env` хеш в
  одинарных кавычках, чтобы Compose не раскрывал `$`). `ensureOwner()` на старте создаёт/обновляет строку `staff(from_env=1)` и
  пользователя `role='staff'` без телефона. Сам пароль нигде не хранится.
- Помощники: `POST /api/admin/staff` (временный пароль один раз в ответе, `must_change=1`), `PATCH /api/admin/staff/:id`
  (`disabled`, `reset_password`, `reset_mfa`, `name`, `note`), `POST /api/me/password` (своя смена; владельцу из `.env` — 409
  `owner_env`). Вход `POST /api/auth/staff` — лимит 30 попыток/IP за 15 мин; **считаются только неудачи**: 10 на логин+IP за
  15 мин и 300 на логин в час (`Limiter.forget` после успеха) — чужой перебор логина владельца не блокирует самого владельца.
  Одинаковое время ответа для чужого логина (dummy-хеш). scrypt N=2^15 с явным `maxmem`; пароль — строка 10…256 символов.
- Таблица `staff` — источник истины (`staffOf` не смотрит на `users.role`): служебный аккаунт не меняет роль (`PATCH /api/me
  {role}` → 409 `staff_account`), не регистрирует магазин, не удаляется. `must_change=1` → любой `needAdmin` отвечает 403
  `password_change_required`; новый пароль не может совпадать со старым.
- `ensureOwner()`: смена хеша или логина в `.env` поднимает `users.token_ver` (старые сессии владельца умирают), удаление
  `OWNER_LOGIN` отключает строку и тоже закрывает сессии; помощник с таким же логином (без учёта регистра) переименовывается в
  `login.old-xxxx` и отключается — старт не падает на UNIQUE.
- `owner_phone` и `free_until` в `PATCH /api/admin/stores/:id` — только владелец (403 `owner_only`); цена доставки магазина —
  только своему отправлению, строгий тип (число или строка цифр с пробелами), не чаще 5 раз в час на отправление
  (`lim "delprice:"`), в боте тот же `deliveryPriceOf`.
- Клиент: `#owner` → шаг `staff` в модалке входа; `user.owner`/`user.staff`; панель `#admin` — владельцу дашборд + «Сотрудники»,
  помощнику — только модерация; обязательная смена временного пароля (`auth.step="pw"`). Вход служебным аккаунтом поверх
  чужого телефонного — `forgetAccountData()`. Служебный аккаунт не видит «Добавить свой магазин» (вместо него — «Панель»).
- Telegram-тревоги: `notify.admins` (модерация, жалобы, новый магазин) — владельцы и помощники с привязанным чатом;
  `notify.owners` (выплаты, возвраты, плата за грузчика, ошибки сервера, бэкап) — только владельцы.

### Уведомления, цена доставки магазина, «Вы заказывали», геолокация (ноябрь 2026)
- Матрица уведомлений (`notify.js` + `disputes.js`/`questions.js`/`masters.js`): заказ оформлен → покупателю (`orderPlaced`,
  для оплаты при получении; карточные — после `paid`), магазину (`shipmentNew` TG+push); принят/собирается/курьер выехал/
  доставлен/выдан → покупателю (`status`); отмена → покупателю и магазину (кроме отмены самим магазином); цена доставки
  названа → покупателю (`deliveryPriced`); жалоба → магазину и админам, ответ → покупателю, решение → обоим; вопрос/ответ;
  снова в наличии; отзыв → магазину; напоминания магазину (20 мин → SMS/TG), прайс раз в неделю; одобрение магазина/мастера.
  Админ-тревоги получают телефоны из `ADMIN_PHONES` и сотрудники (`staff`) с привязанным Telegram.
- Цена доставки магазина (этап 0): `PATCH /api/seller/shipments/:id { delivery_price }` (0…5 000 000, только `delivery_by=store`,
  статусы new/assembling/on_way) → `shipments.price` + `price_named_at`; в ответах заказа `del_store` и `ships[].delivery_price`;
  в кабинете поле «Стоимость доставки» в строке заказа; в боте после «Принять» состояние `delprice` (число или `/skip`).
  Покупатель видит «К оплате при получении: товары + доставка». Платформа цену не выдумывает: до ответа магазина — «уточнит магазин».
- Клиент: наблюдатель активных заказов на любой странице (8 с в окне заказа, ~30 с иначе) → тост + звук при смене статуса/цены;
  «Включить уведомления?» (push на устройстве / Telegram, «Позже» = 3 дня) в окне заказа, списке заказов и кабинете продавца —
  браузерный запрос разрешения открывается только по нажатию.
- «Вы заказывали»: `boughtBefore()` из `orders` (не отменённые), рейл на главной (`data-w="bought"`, по умолчанию сразу после
  инструментов) и список в пустой корзине; `data-bought="id|q|store"` — повтор позиции с прошлым количеством и магазином;
  «Повторить последний заказ» → существующий `repeat`. Заказы подгружаются при входе и на старте (`fetchOrders`).
- Геолокация: карта адреса и карта магазина при открытии без метки сами запрашивают позицию (`locate(true)` / `gpsLocate(true)`);
  отказ помнится 24 ч (`imorat.geoAsk`), `permissions.query` блокирует повтор после «Блокировать»; приложение: разрешения
  ACCESS_COARSE/FINE_LOCATION (Android) и `NSLocationWhenInUseUsageDescription` (iOS).
- Кабинет продавца: «Первые шаги» (одобрение → товары → Telegram → точка на карте → первый заказ) с кнопками; страница для
  магазинов без аккаунта — «Как это работает» на условиях этапа 0.

## Принятые решения
- Один файл сайта без сборщика и фреймворков — чтобы работать с GitHub Pages, в WebView и офлайн.
- Сервер без зависимостей — один `node` и один файл SQLite; бэкапы — копия файла.
- Цены всегда считает сервер (`/api/quote`), клиент только показывает.
- Все заказы оплачиваются только картой на сайте (одна сумма за товар и доставку). Наличных и рассрочки нет: курьер Яндекса деньги
  не берёт, а продавцы не доверят депозит для комиссии с наличных. Пока ключей Payme/Click нет, оформление закрыто («оплата скоро»,
  API отвечает 503 `payments_off`). `ALLOW_PAY_AT_STORE=1` — служебный режим «оплата магазину при самовывозе» без комиссии и бонусов.
- Деньги магазину — по запросу: `payout_available` в кабинете, «Вывести» → `POST /api/seller/payout` → админ переводит и отмечает
  `PATCH /api/admin/payouts/:id {status: paid|rejected}`; переводим в тот же рабочий день.
- Разгрузка при оформлении (`form.help`): `none` — покупатель забирает у машины (`skip_door_to_door`), `one` — курьер донесёт до двери
  (бесплатно у курьера, у грузового тарифа `LOADER` за этаж, минимум один), `two` — два грузчика (×2). В заявку Яндекса уходит
  `cargo_loaders`, продавец видит выбор в карточке заказа и в Telegram. Старое поле `lift: true` читается как `one`.
- Адрес для курьера: улица/дом, подъезд, этаж, квартира, домофон, «частный дом», точка на карте (`la/lo`) — всё уходит в заявку
  Яндекс Доставки (`courier.js`: claims/create → accept → info/performer-position/tracking-links). Покупатель видит курьера на карте
  в заказе (`liveMapHTML`, опрос `/api/orders/:num/courier` раз в 10 с); без токена Яндекса сервер отвечает `unavailable`, и покупатель
  видит настоящий статус и «Местоположение курьера недоступно» — координаты не выдумываются (`COURIER_SIMULATION=1` только для тестовых серверов).
- Английские термины: «мастера» → *Pros*, «виджеты» → *Widgets*, валюта *UZS*.

## Экономика скидок и бонусов — кто платит

Магазин получает полную цену товара по строкам отправления (`shipments.goods` = Σ `price × q` по ценам **после оптовых ярусов**),
минус комиссия и эквайринг. Всё, что уменьшает сумму покупателя сверх этого, оплачивает платформа:

Все скидки сейчас выключены по решению владельца: переключатель `DISCOUNTS_ON` в `.env` сервера (по умолчанию 0; в демо — `DEMO_DISCOUNTS` в странице). Когда выключено, сервер не даёт оптовых ярусов, скидки за комплект, промокода и −10% за «завтра 10–14», а сайт их не показывает; `/api/config.discounts` говорит сайту, что показывать.

| Скидка | Где считается | Кто платит | Включено сейчас |
|---|---|---|---|
| Оптовые ярусы −3% (от 10 шт или роль «мастер») и −6% (от 50 шт) на `tierCats` | `pricing.tierOf` → цена строки | **магазин** (цена строки ниже базовой) — **в договоре с магазином это не прописано, нужно либо прописать, либо перенести на платформу** | нет — `DISCOUNTS_ON=0` |
| Скидка за комплект (`bundleOff`) | `quote.disc` | платформа | нет — `DISCOUNTS_ON=0` |
| Промокод `IMORAT5` (5%, с потолком) | `quote.pd` | платформа | нет — `DISCOUNTS_ON=0` |
| Баллы (до 20% товаров) и кешбэк 1%/2%, приветственный и реферальный бонусы | `bonus.js` | платформа; `BONUS_MONTHLY_BUDGET` — потолок | нет (`BONUS_ON=0`) |
| VIP-тариф (был: бесплатный курьер от 500 000, грузовой −50%, точный час без доплаты, кешбэк 3%) | — | — | **убран** по решению владельца: `/api/me/vip` с `on:true` → 410 `vip_removed`, в `quote` VIP-льгот нет. «Точный час» остался платной опцией для всех (+`fees.VIP_HOUR_FEE`, ключ `when="vip"` — старое имя). Заказам, оформленным с VIP-кешбэком раньше, начисляется обещанный `BONUS_RATE_VIP` |
| Доставка «завтра 10–14» −10% | `quote` | платформа | нет — `DISCOUNTS_ON=0` |

**Оплата магазину напрямую (`pay: store|cash`, весь этап 0):** деньги через платформу не проходят, поэтому `quote` обнуляет всё, что
платила бы платформа — промокод, скидку за комплект, баллы — и не продаёт услуги монтажа (`quote.pay_at_store=true`,
`quote.not_applied=[...]`). Иначе покупатель платил бы магазину сумму, о которой магазин не знает, и никто не был бы должен разницу.

При комиссии 1% (0% первые три месяца) любая из этих скидок делает заказ убыточным для платформы; доходность
складывается из комиссии после третьего месяца и не покрывает кешбэк 1–2%. Решение о ставках и включении бонусов —
за владельцем; код ничего не включает сам.


### Поддержка, комментарии, отмены (ноябрь 2026)
- `server/src/support.js`: таблица `support_msgs`, `GET/POST /api/support` (свой тред, `?peek=1` — только счётчик непрочитанного), `GET /api/admin/support`, `GET/POST /api/admin/support/:uid` (владелец и помощники). Первое сообщение за 30 мин — тревога команде в Telegram; ответ уходит человеку в Telegram и push. Клиент: круглая кнопка «Поддержка» на всех страницах, `#support`, ссылка из заказа (номер заказа прикрепляется), раздел «Поддержка» первым в панели.
- Отмена заказа покупателем: причина (`changed|cheaper|wrong|long|delivery|other`) + комментарий (для `other` обязателен) → `shipments.cancel_note`, магазин видит её в Telegram и кабинете.
- «Нет в наличии» у продавца: необязательная записка `note` (чего нет, чем заменить) → покупатель получает её в уведомлении и в заказе.
- Комментарий к заказу прямо в корзине (`form.comment`), тот же, что в оформлении; виден магазину и курьеру.
- Модерация (`server/src/moderation.js`): товар, который магазин создаёт вручную или из прайса, получает `products.review='pending'` — его нет в каталоге и его нельзя заказать, пока владелец или помощник не нажмёт «Одобрить» (`POST /api/admin/products/:id/review {ok, note}`; отказ — только с причиной, она уходит магазину в Telegram). Текст и фото отзывов (о магазине и о товаре) ждут `mod='pending'`; звёзды с реального заказа учитываются сразу. Очередь: `GET /api/admin/moderation`, блок «На проверке» вверху панели. `PRODUCT_AUTO_APPROVE=1` выключает проверку (тесты, частное демо).

## 3D-модель товара по фото продавца (своя AI, TripoSR)

Новый товар в кабинете продавца публикуется только с фото. Кнопка «Создать 3D с помощью AI» ставит задачу в очередь
(`server/src/model3d.js`, таблица `m3d_jobs`, статусы `pending → processing → completed | failed`; у товара `m3d_state`
`pending|processing|completed|published|failed`). Тяжёлая работа в HTTP-запросе не выполняется. Обработчик
`server/ai3d/worker.py` (открытая нейросеть TripoSR, MIT) работает на Mac (MPS/CPU) или отдельном сервере. Он сам забирает задачи
по HTTPS с токеном `MODEL3D_WORKER_TOKEN`:
- `POST /api/worker/model3d/next` — взять задачу;
- `GET …/:id/photo` — скачать фото;
- `POST …/:id/result` — отдать GLB; сервер проверяет его через `glbProblem`, повреждённый файл не сохраняется;
- `POST …/:id/fail {error, retry}` — сообщить об ошибке;
- `GET …/ping` — проверка связи.

Брошенная задача через `MODEL3D_JOB_TIMEOUT_MS` возвращается в очередь (до 3 попыток). Новое фото отменяет задачу и убирает
старую модель. Повторный запрос на то же фото не создаёт вторую задачу. Лимит на магазин — `MODEL3D_PER_STORE_DAY`,
очередь — `MODEL3D_MAX_QUEUE`.

Продавец в окне видит оригинальное фото и настоящий статус: место в очереди, «AI-обработчик сейчас не в сети», «строит».
Готовую модель он крутит и выбирает «Сохранить 3D» (`POST …/model3d/publish`), «Повторить» или «Удалить 3D» (`DELETE …/model3d`).
Фото не меняется никогда. Покупатель видит переключатель «Фото / 3D» только у опубликованных моделей (`/api/catalog`, поле `m3d`).

Просмотрщик — Three.js r170 (`vendor/three-r170/`, MIT, без CDN; грузится только при открытии 3D). Он умеет:
- вращение мышью и пальцем, приближение колесом и щипком;
- подгонку камеры под модель, мягкую тень и индикатор загрузки в процентах;
- пометку «скрытые стороны примерные».

Без токена функция честно выключена (`/api/config.model3d=false`). Инструкция для Mac, проверка и круглосуточная работа описаны
в `server/ai3d/README.md`.

Тесты:
- `python3 -m unittest discover -s server/ai3d/tests` — сетка и GLB;
- в `api.test.mjs`: очередь и проверки сервера, плюс настоящий цикл `worker.py` с тестовым движком вместо TripoSR;
- браузерный сценарий m3dflow.

Сам вывод TripoSR в CI не запускается: нет torch и весов модели.

## AI-фотостудия: белый фон без изменения товара

Кнопка «Белый фон (AI)» у своего товара в кабинете ставит задачу вида `cutout` в ту же очередь `m3d_jobs`. Колонка `kind`
различает `m3d` и `cutout`. Старый обработчик без поля `kinds` в `/next` такие задачи не получает.

Обработчик (`server/ai3d/cutout.py`) строит **только маску** моделью сегментации (rembg, IS-Net). Пиксели товара он копирует на
`#FFFFFF` бит в бит; меняется лишь кромка 2 px. Результат должен быть без потерь: сервер (`losslessImage`) принимает PNG или
WebP VP8L, JPEG и сжатый с потерями WebP отклоняет. Рука на товаре приходит предупреждением `hand` (заголовок `X-Cutout-Warn`).

Поля товара:
- `img_orig` — оригинал, пока в карточке белая версия;
- `cut_img` — сама белая версия;
- `cut_state`: `pending|processing|ready|applied|failed`;
- `cut_warn`: `hand|edge`.

Маршруты:
- `GET/POST /api/seller/products/:pid/cutout`;
- `POST …/cutout/apply` — «Использовать белый фон»;
- `POST …/cutout/revert` — «Вернуть оригинал»;
- `DELETE …/cutout` — «Оставить оригинал».

Задачи (3D и белый фон) всегда делаются из оригинала (`img_orig || img`). Новое фото удаляет оригинал и белую версию прежнего.
В окне продавца — «До / После», настоящий статус и предупреждение «Пожалуйста, сфотографируйте товар без рук и посторонних
предметов» с кнопкой «Переснять фото».

Тесты:
- `ai3d/tests/test_cutout.py` — пиксели бит в бит, белый фон, кромка, файлы без потерь, рука, край кадра;
- в `api.test.mjs`: очередь, правило «только без потерь», До/После, сохранение оригинала, сверка файла пиксель в пиксель;
- браузерный сценарий studioflow.

### Движение на телефоне (ноябрь 2026)
- **Каталог** (вкладка «Каталог», `openMega` при `isPhone()`): отдельный экран как в IKEA — круглая кнопка «назад» вместо крестика,
  список разделов с картинками и стрелками; раздел (`data-mk` → `mkOpen`) въезжает справа со своими подразделами и «Показать все»;
  назад — кнопкой, Android-кнопкой (`mkBack`) или свайпом от левого края (`mkSwipe`). На компьютере — прежние колонки.
- **Переходы между экранами** (`pageSlide` в обработчике `hashchange`, только телефон и без reduced-motion): новый экран въезжает
  справа поверх замороженной копии старого (`.pg-ghost`, без внутренних id, ниже шапки), назад — наоборот, с возвратом к месту
  прокрутки (`navStack`). Вкладки нижней панели начинают стек заново и меняются мягким появлением. Android «назад» идёт по стеку.
- **Панель корзины/профиля**: шаг внутри (корзина → оформление, профиль → заказы → заказ) въезжает справа, «назад» — слева (`dv-fwd`/`dv-back`).
- **Экран адреса** на телефоне въезжает справа и уезжает обратно.
- Касания: без серой вспышки и задержки двойного тапа; строки списков подсвечиваются, плитки слегка сжимаются.

### Нажатия и переходы как в образце владельца (10 ноября 2026)
Образец — видео приложения-кошелька на Flutter (тёмная капсула навигации с белым кругом, экран собирается по блокам,
суммы «докручиваются»). Сделано в `src/page.html` (блок «Motion like a native app» рядом с `tbPill`):
- **Нижняя панель** (телефон): тёмная капсула по центру шириной по числу вкладок (`--tb-n`: 5 у покупателя, 3 у мастера,
  4–5 у панели); текущая вкладка — на белом круге, который на нажатие одним движением едет к новой иконке (`tbPill`,
  ~0,3 с); старая иконка светлеет, новая темнеет, когда круг доезжает. Пока нажатие закрывает и открывает панели
  (`tbTap`), круг ждёт и потом едет один раз.
- **Нажатие** (`pressStart`/`pressEnd`, любые указатели): кнопка или карточка проседает примерно на 5 px со всех сторон
  (свойство `scale` через Web Animations — не мешает `transform` наведения) и отпускается пружиной с маленьким перелётом;
  короткий тап всё равно доходит до дна. Картинка или название карточки — проседает вся карточка. Длинные строки
  списков только подсвечиваются. У ленты со snap-прокруткой привязка на время нажатия выключается, иначе лента дёргается.
- **Сборка экрана** (`cascade`): блоки на экране по очереди поднимаются на 16 px и проявляются (до 12 блоков, шаг 38 мс);
  высокий блок раскрывается на части (герой — заголовок, поле, цифры; сетка — карточки). Работает при смене экрана
  (`routeTo`, вместо прежнего мягкого появления; на ПК с View Transitions — как раньше) и при нажатии вкладки на
  телефоне (`tabCascade`). Корзина, профиль и инструменты на телефоне — вкладки: открываются сразу, без выезда сбоку,
  и собираются по блокам; при переключении вкладок старая панель исчезает сразу (`html.tb-swap`), без наложения двух
  экранов. Свайп в сторону по-прежнему закрывает панель.
- **Цифры** (`cuScan`/`cuRun`): цифры героя и KPI панелей при сборке экрана считаются от нуля; «Итого» корзины и сумма
  на кнопке оплаты при изменении докручиваются от старого значения к новому (с нуля денежные суммы не считаются).
  Настоящий текст всё время в странице (скринридеры, копирование, тесты), крутящееся число рисуется поверх (`.cu-run::after`).
- При «уменьшить движение» в системе ничего из этого не работает. Проверка — `motion.js` (в `runall.sh`).

### Телефон — приложение, а не сайт (10 ноября 2026)
На экранах до 760 px (браузер телефона и установленное приложение) интерфейс устроен как у магазинов-приложений; компьютер — прежний сайт.
- **Верхняя панель** (`renderHeader`, блок `.ab-top`/`.ab-back`, класс `html.r-home`): на главной — «Доставка · район» (выбор района),
  метка «демо», язык, поддержка (с числом непрочитанных) и избранное; под ними поиск. При прокрутке верхний ряд уезжает, поиск
  остаётся сверху (`.hdr` sticky с отрицательным `top: -var(--abt)`). На остальных экранах — круглая «назад» (`app-back`: шаг по
  `navStack`, иначе главная) рядом с поиском. Меню ☰, логотип, тема и язык из шапки сайта, хлебные крошки, подвал, плавающая
  кнопка поддержки и «Настроить главную» на телефоне скрыты (тема и язык — в профиле, язык ещё и в верхней панели главной).
  Рабочие окна (продавец, мастер, панель) не менялись.
- **Главная** (`HOME_W`, `homeIds`, `PHONE_ORDER`): вместо большого рекламного блока — баннеры возможностей (`promoHTML`: Usta AI,
  AI-дизайнер, список по фото, мастера — всё работающие функции, без акций и обещаний), листаются пальцем, точки под ними, сами
  перелистываются раз в 5 с, пока их не трогают (`promoRun`, не при «уменьшить движение»); затем инструменты, категории, «Вы
  заказывали», хиты, комплекты, мастера, магазины лентой вбок и в конце лента «Популярные товары» (`popularHTML`, по числу отзывов).
  Блоки сайта (герой, преимущества, бегущая строка, «как работает доставка», AI-дизайнер, «для магазинов») на телефоне не
  показываются и не предлагаются в «Настроить главную» (`DESK_ONLY`), баннеры и лента — только на телефоне (`PHONE_ONLY`).
- **Вкладки** «Корзина», «Профиль», «Инструменты» — без ✕ и с крупным заголовком (`.tabroot`); поддержка, избранное и сравнение не
  подсвечивают ни одну вкладку. Сортировка каталога и фильтры мастеров — «пилюли». Долгое нажатие на кнопку или картинку не
  выделяет текст и не открывает предпросмотр ссылки.
- Без входа «Профиль» по-прежнему открывает вход (решение от 1 ноября); в окне входа есть ссылки для продавцов, мастеров и сотрудников.
  Вошедшим в профиле добавлены «Помощь» (поддержка) и «Документы» на телефоне.
- Проверка — `appshell.js` (в `runall.sh`).
- Исправлено: «Назад» после закрытого раньше окна товара возвращал главную на старое место прокрутки (браузер сам
  восстанавливал позицию пропущенной записи истории). Теперь `history.scrollRestoration = "manual"` — позицию экрана хранит
  приложение (`navStack`). Проверка — `backpos.js`.
- Исправлено по снимку владельца: ленты на главной (мастера, магазины, хиты, комплекты, баннеры) останавливались между
  карточками — крайняя слева была обрезана. Причина — нажатие выключало привязку ленты на время «проседания», и свайп,
  начатый с карточки, шёл без привязки (iPhone потом не выравнивает). Теперь привязка возвращается сразу при начале свайпа,
  при следующем касании и при прокрутке колесом (`snapOn`). Карточки мастеров в ленте одной ширины (раньше первая была во
  всю ширину из-за базового правила `.mgrid`), «Позвать» внизу каждой карточки, «пример анкеты» — строкой над именем, а не
  поверх него. Проверка — `rails.js`.

### Оформление и экран заказа в стиле приложений доставки (ноябрь 2026)
- **Оформление** (`dCheckout`): «Доставка / Самовывоз» — сегментный переключатель (те же `input[name=mode]`); над карточкой адреса —
  превью карты OSM с меткой (`ckMapInner`, `#ckMap`, обновляется после экрана адреса); у каждого магазина миниатюры товаров с количеством;
  сводка (`#totals`) — карточка в конце формы; в подвале «Итого» (`#ckTotal`, следит за `#totals` через MutationObserver) и большая кнопка.
- **«Оформить заказ?»** (`askOrder`): после проверки формы — окно «Куда / Оплата / Итого», «Отмена» / «Подтвердить» (`#ckGo`); только после
  подтверждения заказ уходит (`submitOrder.ok` — на один проход). Кнопка показывает спиннер (`.btn.busy`). Тесты жмут `#ckGo` после `#payBtn`.
- **Экран заказа** (`dTrack`, панель с классом `trk`): карта сверху (`liveMapHTML(..., big)`: магазин, адрес, курьер — только если перевозчик
  дал позицию), над ней кнопки «назад», «Заказ №», «центрировать»; лист, который заезжает на карту при прокрутке: «Live · м:сс» (в демо — «Демо»),
  шаг словами (`trkTitle`), время до прибытия — только когда курьер едет и есть `eta_min` (`trkEtaHTML`), полоса шагов, курьер
  («имя · машина · номер» от Яндекса, в демо — демо-данные с пометкой), хронология с реальным временем, «Откуда / Куда» с расстоянием по прямой,
  состав и оплата, отзыв о магазине после доставки, «Повторить» / «Продолжить покупки». Несколько магазинов — чипы `data-trkship`.
  Обновления курьера меняют текст на месте (`trkLive`), новый шаг перерисовывает экран. Телефона курьера и магазина в данных заказа нет —
  кнопки звонка нет; есть «Написать в поддержку» и «Открыть в Яндекс Go», если есть ссылка.


### Категории на компьютере, очистка корзины, профиль (ноябрь 2026)
- **Сетка категорий на главной** (`[data-w="cats"] .cat-grid`): на компьютере картинка сверху, под ней название (до двух строк)
  и число товаров, ряды одинаковой высоты (`grid-auto-rows: 1fr`). «Весь каталог» занимает все свободные ячейки последнего ряда
  (`catSpan()`, после `applyHome` и при изменении размера окна) и тогда показывает полосу картинок других товаров
  (`.all-th`, класс `wide`, высота `--ih` как у картинок плиток). На телефоне лента в два ряда не менялась.
- **Боковая панель каталога**: числа товаров стоят на строке названия (`align-items: baseline`).
- **«Очистить корзину»** (`data-act="cart-clear"`, строка `.cart-top` над корзиной): корзина, услуги и комплекты очищаются
  сразу; в уведомлении 6 секунд есть «Вернуть» (`toast(текст, мс, { label, fn })` — уведомление с кнопкой).
- **Профиль** (`dProfile`, панель с классом `prof`; класс `.pf` уже занят рамкой фото в жалобах и отзывах): шапка с аватаром,
  именем, телефоном и метками (роль, способ входа); четыре счётчика (заказы, избранное, проекты, слежу за ценой); последний
  заказ строкой со статусом; «Кто вы?» — плитки с иконками и галочкой (`rolesHTML(..., true)`, `.roles.rich`); группы как в
  настройках iOS (`.pf-group`, `.pf-row`): уведомления, район, тема, язык, оформление; «Ремонт и покупки»; «Для бизнеса»;
  «Выйти» и удаление аккаунта красным. Подвала нет, список уходит под нижнее меню; линия под заголовком появляется при
  прокрутке (`#drawer.scrolled`).
- **Шапка на телефоне** — одна строка: меню, логотип, «ДЕМО», тема, язык. Язык — компактная кнопка «UZ ▾» (`.lang-pick`,
  поверх неё прозрачный `select[data-langsel]`, список «Русский / Özbekça / English»); три кнопки RU/UZ/EN остаются на компьютере.
  На экранах ≤370px кнопка темы скрыта (тема есть в профиле).
- **Серая полоса над шапкой на iPhone**: iOS Safari красит строку состояния цветом фиксированного слоя у верхнего края, и
  прозрачное затемнение `#scrim` давало серый. Теперь `#scrim` выключается через `visibility: hidden`, когда ничего не открыто.
- **Заставка и строка состояния iPhone**: фон самого `#intro` меняется вместе с картинкой (светлый → тёмный к ~1,2 с, `inBg`;
  снова светлый при растворении, `inOut`), потому что iOS Safari красит строку состояния цветом этого слоя. Заставка убирается
  только по концу `inOut`, а не по концу `inBg`.

### Регистрация и вход по паролю, путь продавца к договору, работы мастеров (ноябрь 2026)
- **Вход** (`renderAuth`, шаг `start`): номер (+998, флаг) и пароль с «глазком», «Забыли пароль?», «Регистрация»; ниже
  «Войти по коду из SMS» (`#aUseCode` → шаг `sms`) — для старых аккаунтов без пароля. Сервер: `POST /api/auth/login`
  (одинаковый ответ на неизвестный номер и неверный пароль, лимиты неудач на номер+адрес и на номер).
- **Регистрация** (шаг `reg`): карточки «Покупатель / Мастер или прораб / Продавец» → номер → SMS-код (номер подтверждается
  один раз) → имя и пароль (≥8 символов, `POST /api/auth/password` с билетом `pw_ticket` из `otp/verify`, 15 минут).
  Мастер выбирает «показывать работы бесплатно» (после входа — анкета мастера и фото работ) или «я прораб» (роль `pro`).
  Продавец после пароля заполняет анкету магазина.
- **Забыли пароль** (шаг `forgot`): SMS-код → новый пароль; смена существующего пароля завершает другие сессии (`token_ver`).
  Пароль хранится как scrypt-хеш (`users.pw_hash`). В демо — PBKDF2-хеш в `imorat.accounts`, не в сессии.
- **Продавец до открытия доступа**: `pending` (анкета на проверке) → `meeting` (админ назначил дату, время и место:
  `stores.meet_at`, `meet_place`) → договор подписывается лично → админ вписывает номер (`contract_no`, `contract_at`,
  `contract_by`) и только так открывает доступ (`contract_required` без номера). В кабинете продавца — шаги пути
  (`storeBanner`), в панели — «Назначить встречу» / «Договор подписан» (`admStoreWay`). Продавцу приходит сообщение в Telegram.
- **Работы мастера**: до 12 фото (`masters.works`, `POST /api/masters/me/works`, `DELETE …/works/:n`); новое фото
  у одобренной анкеты возвращает её на проверку. Галерея в кабинете мастера и в публичной анкете.
- Политика конфиденциальности дополнена (пароль как хеш, данные встречи и договора), редакция от 8 ноября 2026.

### Отдельные окна после входа и отдельные страницы входа (ноябрь 2026)
- `workMode()` → `admin` | `seller` | `master` | null. Классы `html.workm` (+ `adminm` / `sellerm` / `masterm`) прячут
  магазин: поиск, каталог, корзину, полосу разделов, подвал, кнопку Usta AI; `renderMain` держит человека в его окне
  (админ — `#admin`, продавец — `#seller`, мастер — `#masters`).
- **Админ и владелец**: панель с разделами «Заявки» (магазины: анкета → встреча → договор; мастера; товары и отзывы на
  проверке), «Жалобы», «Поддержка», у владельца — «Обзор» (цифры, финансы, сотрудники). На компьютере — вкладки
  (`.adm-tabs`, `data-atab`), на телефоне — своя нижняя панель. Маркетплейса в окне админа нет.
- **Продавец**: кабинет магазина (как раньше), **мастер**: «Заявки» и «Анкета и работы» (`renderMasterWork`, `data-mwtab`).
  У обоих кнопка «Открыть маркетплейс» в шапке; в маркетплейсе — тёмная полоса «Вернуться в кабинет» (`.work-back`).
  Мастер определяется по анкете (`/api/masters/me`) или по отметке после регистрации (`imorat.masterAcct` = id пользователя).
- **Страницы входа**: `#partner` — «Вход для продавцов и мастеров» (тот же номер и пароль, регистрация только мастер или
  продавец), `#staff` — «Вход для сотрудников» (логин и пароль от владельца). Обе без витрины (`html.loginm`); шаги входа те
  же (`openAuth(..., page)` рисует их в `#authPage`). Ссылки — в подвале «Партнёрам» и внизу обычного окна входа.
- **Все магазины по отдельности** (владелец, «Обзор»): таблица всех магазинов за выбранный период — заказы, оборот, срывы,
  скорость принятия, рейтинг, товары и нехватка, открытые заказы и жалобы, последний заказ; поиск по названию или телефону
  владельца и сортировка. Нажатие на магазин открывает его страницу: показатели, оборот по дням, последние заказы, что
  покупают, свежие отзывы. Сервер: `GET /api/admin/stores-overview?days=`, `GET /api/admin/stores-overview/:id` (только
  владелец). В демо — цифры, построенные из id магазина, с пометкой «демо-данные»; магазин, зарегистрированный в демо,
  начинает с нуля.
- **Демо: анкеты магазинов у админа.** Раздел «Заявки» в демо показывает магазины, зарегистрированные в этом браузере, и
  те же кнопки (встреча → договор → доступ) меняют их статус — продавец видит это в своём кабинете.
- **Шапка окон и страниц входа**: начиная с кнопки темы всё прижато вправо.

### Исправления по ручной проверке (8 ноября 2026)
- **Оформление заказа**: платная помощь с разгрузкой больше не включена заранее — итог в оформлении совпадает с итогом
  корзины; цена у варианта считается так же, как в `quote()` (за этаж и за каждую грузовую машину).
- **Кнопка «Назад» телефона/браузера** закрывает открытое окно товара, корзину, меню, Usta AI или окно входа и остаётся
  на той же странице (`histPanel`: запись в истории на время окна; после закрытия крестиком запись помечается
  использованной и следующий «Назад» её пропускает — без `history.back()` в момент закрытия, чтобы не мешать переходу,
  начатому сразу после).
- **Магазин до договора не продаёт** (демо): его новые товары и цены не попадают в каталог (`HELD`), в кабинете они
  с пометкой «ждёт договора»; после «Договор подписан» товары появляются в каталоге. В своём магазине больше нет
  выдуманных заказов — только реально оформленные в этом браузере. Продавец видит только свой магазин (без списка чужих).
- **Цена у продавца**: «только у вас», если других предложений нет; «как у других» при равной цене. Форма добавления товара
  предупреждает, если такой товар уже есть в каталоге, и предлагает продавать его по своей цене (демо — сразу, на сервере —
  заполняет форму «Продавать товар из каталога»).
- **Владелец**: встречу нельзя назначить в прошлом или дальше чем на год (и в браузере, и на сервере — `meeting_past`), в дате
  показывается год, если он не текущий. «Отметить проверенным» и «0% +3 мес» работают в демо. Цифры «Обзора» в демо
  складываются из тех же цифр по магазинам, жалобы и вопросы — только реальные из этого браузера. Владелец и модератор
  могут открыть маркетплейс и вернуться в панель кнопкой.
- Мелочи: название магазина в шапке обновляется после изменения; ссылка «Мастера» в шапке закрывает страницу мастера;
  поля часов работы не вылезают за карточку на телефоне; сумма на кнопке оплаты не разрывается; итог корзины на
  телефоне компактный (строки «Товары» и «Доставка» — по стрелке); в анкете мастера нет заранее выбранного района и опыта;
  «74 работы»; «Гарантия» в сравнении — как на странице товара; у демо-оценок товара — пояснение, что они примерные.
- **Даты на узбекском** форматируются вручную для `uz-Latn-UZ` (названия месяцев и дней недели, новая орфография через
  `uzNew`): в части браузеров нет узбекских данных календаря, и вместо «Seş, 10-noyabr» выходило «M11 10, Tue».

### Полоса под строкой состояния при запуске (8 ноября 2026)
- Заставка тёмная с первого кадра, и полоса под часами/батареей телефона тоже: маленький скрипт до отрисовки ставит
  `html.intro-on` (тёмный фон страницы — его берёт Safari на iPhone) и `theme-color #171412`; когда заставка начинает
  гаснуть, `showIntro()` возвращает цвета темы (`applyLook`). Без заставки цвет шапки ставится сразу.
- В приложении (Capacitor) нативная строка состояния берёт тот же цвет (`nativeBar`); заставка запуска приложения,
  строка состояния в `capacitor.config.json` и цвета запуска в `manifest.webmanifest` — тёмные `#171412`.
- Сборка проверяет каждый встроенный `<script>` отдельно (`node --check`).
- Заставка перерисована под тёмный старт: вместо трёх ромбов (на тёмном фоне они вспыхивали серым) — тёплое свечение
  за знаком и расходящиеся контурные ромбы; подложка знака тёмная сразу. На выходе сначала гаснут знак и надпись,
  потом поднимается тёмный фон — без «призрака» заставки поверх магазина.

### Надёжный пароль (9 ноября 2026)
- Новый пароль вводится **два раза** (регистрация, «Забыли пароль», смена пароля сотрудника) — живой список правил
  отмечает выполненное, полоска показывает силу (слабый → надёжный).
- Правила одинаковые в приложении (`pwFlags`) и на сервере (`passwordProblem` в `server/src/auth.js`, сервер решает):
  не короче 8 символов (сотрудники — 10); буквы и цифры; не одни и те же символы и не повтор кусочка (11111111,
  ab12ab12ab12); без рядов из 5 символов подряд по алфавиту, цифрам или клавиатуре и без 4 одинаковых подряд (12345,
  abcde, qwerty, йцуке, 1111); не популярный пароль и не построенный на популярном слове (password1, parol2024,
  toshkent2024); без номера телефона и имени (имя сравнивается и кириллицей, и латиницей: Азиз → aziz).
- Сервер отвечает `weak_password` с причиной `reason` (short / same / run / mix / common / personal / same_as_old),
  форма показывает понятный текст. Проверка дешёвая и идёт до лимита попыток. `tools/owner.mjs` (пароль владельца)
  проверяет те же правила.

### Проверка безопасности и исправления (9 ноября 2026)
Независимая проверка кода (вход, доступ к чужим данным, оплата, загрузки, заголовки, секреты, лимиты). Критичных дыр нет;
SQL-запросы параметризованы, чужие заказы/товары/чаты недоступны, колбэки Payme/Click проверяют подпись и сумму.
Исправлено:
- **XSS через описание магазина** (было опасно: код мог выполниться у всех, включая владельца): описание выводится
  через `esc()`, сервер вырезает `<>` из всех текстов магазина (вместе с описанием и реквизитами).
- **Content-Security-Policy** на собранном сайте (`tools/build_site.py`): выполняются только встроенные скрипты сайта
  (по SHA-256), его файлы и Яндекс Карты / вход Google и Apple; встроенные обработчики `on…=` из приложения убраны.
  Проверка `csp.js`: внедрённый `<img onerror>` не срабатывает. Caddy добавляет HSTS, запрет встраивания в чужие
  страницы (frame-ancestors / X-Frame-Options) и Permissions-Policy; API — HSTS и nosniff. (GitHub Pages заголовки не
  ставит — там действует только CSP из страницы.)
- **Реквизиты выплат**: новая карта/счёт — только с паролем аккаунта (без пароля первую карту заменить нельзя:
  `need_password`); владельцу магазина уходит сообщение в Telegram и SMS, владельцам площадки — в Telegram, в журнале
  `payout.change` (номера замаскированы). Текст SMS нужно согласовать как шаблон в Eskiz.
- **Payme**: тестовый ключ не принимается на боевом сервере (сервер не стартует с `PAYME_TEST_KEY`, кроме
  `PAYME_SANDBOX=1` на время проверки Payme); ключи сравниваются за постоянное время.
- **Лимиты**: IPv6-адреса считаются по сети /64; общий бюджет SMS (`SMS_PER_HOUR` 400, `SMS_PER_DAY` 4000); лимиты
  Usta AI проверяются до чтения тела запроса, у гостя тело до 2 МБ и короче тексты; не больше 3 неоплаченных заказов
  на аккаунт и до 20 000 шт. в строке; код из приложения-аутентификатора — не больше 30 попыток в день, после 5 ошибок
  за час владельцам уходит предупреждение.
- **Push-подписки** — только адреса настоящих push-сервисов (FCM, Mozilla, Apple, Windows, Яндекс).
- **Сброс пароля**: ссылка-разрешение после SMS работает один раз. Коды для проверяющих магазинов приложений — 6–8 цифр,
  неверные попытки не обнуляются.
- **Запуск в production**: `JWT_SECRET` не короче 32 символов; демо-магазины не создаются (только при `DEMO_STORES=1`).
- Изменения открытого магазина (название, описание, адрес, телефон, Telegram) пишутся в журнал и отправляются
  модераторам; названия товаров на проверке не попадают в подсказки Usta AI.
Не сделано (решение за владельцем): подтверждение получения покупателем перед выплатой магазину, удержание выплат
после смены карты, блокировка выплат при открытой жалобе; CAPTCHA для SMS; отзыв токена при выходе с одного устройства.
